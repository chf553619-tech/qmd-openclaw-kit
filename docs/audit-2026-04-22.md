## Token-efficiency analysis

## Important limitation

This section does **not** claim an exact billing delta from provider-side usage logs.

Instead, it estimates **context tokens likely sent to the LLM** under two patterns:

1. **Without QMD**: reread several candidate docs directly
2. **With QMD**: search first, then read only the most relevant docs

That is the correct operational comparison for this deployment because QMD is being used as a **local retrieval layer to reduce unnecessary rereads**.

|---|---:|---:|

### Interpretation

The value of QMD in this deployment is not that every question becomes magically free. The value is that it narrows the reread set.

In practice, this deployment is already capable of cutting context payload roughly by:

- **~33%** in broader multi-doc cases
- **~42%** in typical deployment troubleshooting lookups
- **~71%** in targeted operational questions

Real savings vary by question, but these estimates are directionally credible because they are based on the actual local docs being retrieved.

## Comparison: with vs without QMD

### Without QMD

Typical agent behavior tends to be:

- reread multiple candidate markdown files
- include large README / setup docs "just in case"
- spend tokens rediscovering where the answer is

This is especially wasteful in OpenClaw-style workspaces where notes, memory, docs, kits, and upstream references all accumulate.

### With QMD

Observed workflow becomes:

- run fast local retrieval first
- identify the likely answer-bearing docs
- read only those docs (or excerpts)
- escalate to heavier rereads only when needed

That makes the deployment meaningfully more efficient even before considering semantic/rerank improvements.
